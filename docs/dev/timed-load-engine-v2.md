\`decisions/TIMED_LOAD_PROGRESSION.md\` (PGE-DEC-002), cross-checked against
\`openspec/changes/progression-engine-timed-load/specs/progression.md\`,

## Controller inputs and state

Pure transition input: a validated per-exercise configuration, a validated
controller state, and full-exposure success/failure. Config includes:
\`setsPerSide\`, \`unilateral\`, \`minTime\`, \`maxTime\`, \`timeStep\`,
\`emergencyTime\`, \`emergencyBehavior\`, a strictly increasing
\`ladderKg\` starting at logical zero, \`lowLoadSwitchKg\`,
\`lowLoadUpStepKg\`, \`downwardLadderSteps\`, and \`startLoadKg\`.
The routine editor derives sets and unilateral mode from its own plan.
The accepted Side Plank configuration requires two sets per side and
30/35/40/45 s. It requires correct technique and both limbs on every set.

Persisted logical state: \`initialized\`, \`load\` (canonical kg),
\`target\` (seconds), \`fails\` (0 or 1), \`provenance\`
(\`new\` or \`established\`), \`emergency\`, \`bridgeTarget\`
(native kg or null), and \`bridgeProvenance\`. The first exposure
calibrates from a conservatively selected native load, never forces a
zero-to-start climb. A missing completed work row produces no transition.
Partial counted exposures fail the full-exposure success criterion.

Normal success below maximum adds one time step; success at maximum adds
the next realizable higher load and resets time, or remains at max when
equipment is topped out. A single failure repeats the same state; two at
a target above minimum back time down one step. At minimum, two failures
on a newly increased load enter temporary 25 s emergency (Side Plank);
a failed emergency backs down a native load step and remembers the failed
load plus *new* provenance. Two failures on an established load at minimum
back down immediately and remember the failed load plus *established*
provenance. Complete the bridge through the normal time ladder; then
return to the exact remembered load and its original provenance. A
deliberate first-set conservative downshift owns the current exposure
and persists as a lower baseline without immediate auto-promotion.
There is **no Turbo** and no benefit for extra hold time.

## Boundary and persistence

- \`api/training-control/timed-load.js\` owns deterministic algorithmic rules.
- \`api/training-control/timed-load-weight.js\` maps exact native kg to/from
  display units; the controller never stores fake kg/lb increments.
- \`frontend/src/lib/timed-load-session.js\` bridges session editable rows
  and the controller, maintaining current-exposure downshift ownership.
- \`frontend/src/lib/session-start.js\` explicitly selects the opted-in
  controller for eligible timed slots; disabled slots use Engine v2.
- \`frontend/src/lib/finish-session.js\` persists the next state in
  \`trainingControl.timedLoad[trackId]\` rather than \`progression\`.
- \`api/training-control/timed-load-history.js\` replays each track's
  last counted exposure per workout in chronological order, ignoring
  excluded/no-work events. Per-exposure \`timedLoad\` snapshots retain
  configuration/provenance; edit, delete, date move and backfill replay.
- \`frontend/src/lib/sync-merge.js\` merges workout records and tombstones
  **first**, then derives Timed Load state from the resulting history:
  editing the same record on two devices never doubles its transition.
- \`frontend/src/lib/units.js\` changes display units on exposure
  snapshots, while controller config/state remain in canonical kilograms.
- \`api/engine/context.js\` excludes Timed Load-owned logs from ordinary
  Engine v2 replay; ATP2's old exclusion remains intact.
- \`frontend/src/components/TimedLoadConfigFields.jsx\` gives explicit
  per-slot configuration and strict errors. New slots default to OFF.

### Configuration edits and equipment replacement

If a previous state remains valid for the new config/native ladder, it is
retained; otherwise it is reset to the new calibration floor. Historic
configurations are frozen with their exposure logs, so replay can rerun
the old transition and validate/adapt the result for the next event.
No non-native load can be *prescribed* by the controller.

### Deload/RTT and non-live boundaries

A caller can suspend control by setting
\`exposure.excludedFromProgression\`; no HYBRID-2/RTT policy is implemented.
No live account, running openGym server, Android installation, existing
routines, or user workout data was changed. Physical-device / live
runtime tests are explicitly deferred.

## Independent review fixes (2026-11-09)

Three regression tests were demonstrated failing before the corresponding changes.

1. First calibration: original Liftoscript update() requires setIndex == 1,
   state.initialized == 0 and completedWeights[1] != weights[1], then updates
   weights[2] = completedWeights[1]. In openGym the unilateral first logical
   set consists of both L and R rows. Once both sides complete at a realizable
   6 kg from an initial 0 kg, subsequent unfinished rows inherit 6 kg.
2. Trigger ownership: an arbitrary completed later row cannot trigger the
   original first-set downshift. First logical set completion (both L and R)
   gates update() and the durable manual-override/calibration decisions.
   Skipped first-set work does not silently calibrate from a later completed
   set. Completed rows are never rewritten.
3. Technique: an explicit techniqueValid: false is retained through
   editable sets, canonical performance, JSON, history replay, editing
   and offline sync conflict resolution. For opted-in Timed Load holds,
   the set menu includes a Technique valid switch. A flagged hold remains
   completed in the log, is visibly marked !, and cannot earn progression
   even when its recorded duration reaches the target.

The 4,976 Python-oracle transition vectors remain unchanged and passing.
The original Liftoscript source was regenerated from fitness's
programs/timed_load_controller.py and checked at the adapter boundary;
live Liftosaur-runtime parity was not claimed. No HYBRID-2, RTT,
production-data edits or physical phone tests were performed.
