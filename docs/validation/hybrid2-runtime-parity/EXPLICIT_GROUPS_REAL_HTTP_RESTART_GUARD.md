## Newly reproduced failure and guarded fix

The original validation-branch implementation correctly prevented grouping changes after training in the frontend UI. A forged HTTP `PUT /api/data` could nevertheless remove `progressionGroups` after logged group workouts, and **the API returned HTTP 200 instead of HTTP 400**. This was reproduced against the actual API server with four completed synthetic sessions, and retained as an expected RED negative control in the original first-run log.

Two separate, complementary guards have now been implemented:

1. **Self-consistency within a canonical profile** (`api/migration/profile-validation.js`): for every exposure with the `progression-group:` prefix or an occurrence currently assigned to a group, the `trackId` must exactly match the occurrence's authoritative group. This rejects missing/replaced group membership without changing existing non-group H2 identities.
2. **Continuity across server revisions** (`api/engine/progression-groups.js` `validateProgressionGroupTransition` invoked by `api/server.js`): compare the previously persisted grouped membership against the proposed profile for every occurrence with completed history. A change to its group identity after training is HTTP 400, even if a malicious/offline writer coherently changes **all** historical exposure track IDs, frozen prescription track IDs and hashes, and progression-state keys. An explicit full profile reset that removes all workout history may begin a clean group configuration.

Without the second guard, the completely rewritten document was canonically valid. The new transition check deliberately rejects it. Existing legacy/ungrouped profiles continue using their established validation and progression behavior.

## Reproducible real HTTP test

`api/test/progression-groups-http-restart.test.js` spawns real `api/server.js` children using an ephemeral `PORT=0` and `DATA_DIR` generated by `mkdtemp`; a local test-only account and HMAC secret are created only inside that temporary directory and deleted in `t.after`. Test-only sessions are generated and completed using **the actual** `buildSessionExposures`, `entriesForExposures`, `buildCompletedSession`, `replayProgression`, `stampEdits` and `mergeStates`.

Verified end-to-end flow: initial packed profile write, readback and disk verification; incorrect-repetition group rejected with HTTP 400; Monday (100 kg) and fifth-position Wednesday (100 kg) completed and persisted; **first actual API restart**; Friday inherited Monday progression (102.5 kg), Wednesday independently advanced (102.5 kg); forged post-history unlink returned HTTP 400; **fully rewritten, internally canonical history rekey** returned HTTP 400; a second client attempted a stale conditional write and received HTTP 409; legitimate offline Wednesday routine-name edit merged with the fifth new Monday session; **second actual API restart**; exact group and independent replay pointers recovered from disk.

**Result: PASS.** 22 real HTTP requests, **7 successful writes, 4 intentionally rejected writes (three HTTP 400 and one HTTP 409)**, 2 server restarts, 5 completed test workouts, server revision 7, and next target **107.5 kg** in the Monday/Friday shared group versus **105 kg** in the isolated Wednesday track. Full [sanitized evidence](explicit-groups-http-restart-sanitized.json) contains no authentication secrets or real user records.

To reproduce:
